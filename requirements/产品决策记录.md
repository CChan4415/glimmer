## 决策 #01：产品形态 = 移动端为主 + Web 看图为辅

- **日期**：2026-08-12
- **决定**：第一版以移动端 App 为主，承载一键导入通讯录；Web 网站同一账号登录，只展示比手机端更精美的关系图，不做导入（浏览器无法访问手机通讯录）。
- **理由**：web 拿不到通讯录（浏览器无权限、微信也不开放第三方通讯录接口），"扫码导入"在纯 web 上不成立；App 端能实现"一键导入"这一核心钩子。Web 的"看图"简洁定位反而成为天然边界。
- **影响**：技术选型需双端（App + Web）；Web 是辅助展示层；技术选型文档中的"Flutter 双端"需补充 Web 策略（见 §设计）。
- **来源**：需求对话 2026-08-12。

## 决策 #02：第一版范围 = 关系资产管理 + 可视化（发现 / 引荐推迟）

- **日期**：2026-08-12
- **决定**：第一版做：注册登录 → 移动端一键导入通讯录 → 生成精美关系图 → 编辑修正 → 关系资产统计 + 通讯录分组（家人 / 同事 / 朋友）着色。**关系发现、引荐请求推迟到第二版**。
- **理由**：单人开发，第一版做小而完整；先验证"用户是否愿意导入通讯录 + 精美图能否带来惊喜"这一最大风险；用户原话"只实现图没意义，但第一版功能先实现这个"。
- **影响**：原 MVP 边界清单的发现 / 引荐相关决策（D2/D6/D7/D8/D9）推迟到第二版处理；首页内容随第一版重心重定（见 §需求重定）。
- **来源**：需求对话 2026-08-12（Q1 → 推荐 B，用户采纳）。

## 决策 #03：标签体系 = 通讯录分组 + 手动标签 + AI 打标（P1）

- **日期**：2026-08-12
- **决定**：第一版标签来源三层：①通讯录自带分组（家人 / 同事 / 朋友）→ 用于图上着色；②手动标签（预设标签库，可选少量）；③AI 自动打标 → P1。
- **理由**：导入的数据只有姓名 + 电话，无兴趣标签；纯手动打标成本高（原对话风险"用户太懒"）；通讯录分组零成本即可做出彩色图。
- **影响**：数据模型需为"联系人可挂多个标签"预留结构；着色依赖分组标签。
- **来源**：需求对话 2026-08-12（Q2 → A + C + 分组，用户采纳）。

## 决策 #05：登录方式 = 手机号 + 微信 + Apple（面向中国大陆）

- **日期**：2026-08-12
- **决定**：首版登录方式定为 **手机号验证码 + 微信 + Apple**，取代原"不用手机号，Apple/Google/邮箱"的设计。
- **理由**：D10 定为面向中国大陆市场。Google 在大陆不可用；国内用户几乎都习惯手机号验证码；微信是国内最高频登录入口；Apple 登录是上架 App Store 的强制要求（凡使用第三方登录，必须同时提供 Apple 登录）。
- **影响**：原"避免社交软件压迫感、不用手机号"的设计仅在海外市场语境成立，中国大陆语境下手机号是最低摩擦方案。决策 #01 中的登录方式相关描述作废。需同时支持三方式登录账号互通（同一手机号/微信/Apple 绑定同一账号）。
- **来源**：需求对话 2026-08-12。

## 决策 #06：第一版"看到朋友的朋友" = 被动浏览（2 度，化名/授权名）

- **日期**：2026-08-12
- **决定**：第一版支持"看到朋友的朋友"，形态为**被动浏览**：在关系图上点开朋友节点，展开显示其朋友（2 度人物），未注册默认化名、注册且授权则显示真名。**不做主动搜索、不做引荐请求**——这两者仍是第二版。
- **理由**：这是"半熟人社交"的核心价值，用户明确要求进第一版；但第一版只做最简形态，主动搜索/引荐的完整交互留给第二版"完善细节"。
- **影响**：第一版范围在决策 #02 基础上扩展（#02 原定发现/引荐整体推迟，现"2 度被动浏览"回到第一版）。2 度人物的身份暴露遵守决策 #04 的化名原则。
- **来源**：需求对话 2026-08-12。

## 决策 #07：隐私控制 = 双向全局开关（对他人 + 对自己）

- **日期**：2026-08-12
- **决定**：第一版隐私控制为**双向**全局开关，默认值如下：
  - **对他人（我导出的数据）**：全局开关"我的联系人是否可被朋友的朋友看到"，**默认开**（展示化名）。
  - **对自己（我在别人网络中的展示）**：① 开关"是否允许我出现在朋友的网络中"，**默认开**；② 展示级别：**仅化名（默认）/ 化名 + 分组** 两档。
  - 按联系人 / 分组的细化配置，第二版再做。
- **理由**：用户明确要求隐私控制需覆盖"自己隐私的展示范围"，而不只是控制自己的数据导出。默认开 + 化名展示符合"展示关系的存在，而不暴露关系的身份"——暴露的是化名，不是身份。
- **影响**：隐私模型从"四层可见性"演进为"真名私有 / 化名公开形象（默认）/ 授权解锁" + 双向开关。数据模型需支持这两个开关与展示级别字段。
- **来源**：需求对话 2026-08-12（用户补充"自己的隐私控制"）。

## 决策 #08：技术栈模块化约束（可快速替换）

- **日期**：2026-08-12
- **决定**：第一版技术栈（尤其关系图渲染引擎、AI 等关键层）必须**模块化、可插拔**：效果不满意或发现更好方案时，能快速替换而不重构业务逻辑。用户原话："效果出来后我不满意或者我找到更好的方案，要支持模块化快速修改技术栈。"
- **理由**：关系图渲染是第一版核心，但引擎选型不确定性高（D-C1 先按 Web 成熟图库 + 移动端轻量图起步）；用户保留对视觉效果挑剔并换方案的权利。
- **影响**：技术选型文档需补充模块化约束；渲染层、AI 层、数据层各自封装独立接口，业务代码不直接依赖具体引擎。这是对 [技术选型.md](../design/技术选型.md) 的追加约束（该文档方向级定稿保留，模块化要求在设计中落地）。
- **来源**：需求对话 2026-08-12（采纳 D-C1 时附带）。

## 决策 #04：隐私原则 = 真名私有，化名是公开形象

- **日期**：2026-08-12
- **决定**：确立产品核心隐私原则：**真名是自己的私密数据，化名是你在别人眼中的公开形象**。
  - 自己导入 / 编辑的联系人：对自己显示真名（私有）。
  - 当自己出现在朋友的网络里：对朋友默认显示化名。
  - 未注册用户：默认只暴露化名 / 昵称（系统无权替未同意过的第三方决定暴露真名）。
  - 认领机制：用户被别人加入关系网后，提示"你的朋友 A 把你放进了他的关系网络，加入后你可控制别人看到什么"——兼作冷启动拉新杠杆。
  - 注册用户可配置自己暴露的信息（如只展示姓名）。
- **理由**：这是"展示关系的存在，而不暴露关系的身份"在数据层的落地；也是隐私合规（第三方数据权）的底线。
- **影响**：覆盖并取代原边界清单 D4 的四层可见性简化版——新的分层是"真名（私有）/ 化名（默认公开形象）/ 授权解锁"。数据模型见《数据模型与隐私设计》。
- **来源**：需求对话 2026-08-12。

## 决策 #09：导入方式 = 手机通讯录为主 + 手动批量 + 手动单个（好友列表 API 全球不可用）

- **日期**：2026-08-12
- **决定**：导入来源为**A（手机通讯录，主）+ B（手动批量添加，表格式界面）+ C（单人手动词条添加）**。未来发现其他批量来源作为 D 补入后续版本。
- **理由**：用户明确要"多种导入方式"；但微信、QQ、Facebook、LINE、WhatsApp、Telegram 均不向第三方开放好友列表 API——这是 Cambridge Analytica 后全球行业的隐私趋势，不是技术限制。手机通讯录几乎是唯一可行的批量导入来源。
- **影响**：通讯录导入体验直接决定关系图质量；手动批量添加（表格界面）是第一版除通讯录之外的用户新增入口。
- **来源**：需求对话 2026-08-12（D-1 确认）。

## 决策 #10：AI 自动分组不进第一版（确认重申）

- **日期**：2026-08-12
- **决定**：**AI 自动分组仍为 P1/第二版**，不进第一版。第一版分组仅来自通讯录自带分组（家人/同事/朋友）+ 手动标签。未分组联系人默认归入"未分组"，不做"朋友"兜底。
- **理由**：用户明确"AI → P1，不提前到 P0"；决策 #03 结论不变。第一版走最简单路径，数据模型的标签结构留好 AI 打标接口即可。
- **影响**：关系图增强功能延期到第二版；第一版分组来源有限 → D-4 不做聚合更合理。
- **来源**：需求对话 2026-08-12（D-4/D-5 确认）。

## 决策 #11：监控 = P1，RPO ≤ 24h / RTO ≤ 4h

- **日期**：2026-08-12
- **决定**：第一版不建专用监控系统（P1），仅服务器日志 + 关键端点健康检查（每 5 分钟 ping）；**RPO ≤ 24h（日备最多丢一天数据），RTO ≤ 4h（挂掉后 4 小时内恢复）**。备份日备加密，保留 ≤ 90 天。
- **理由**：单人运维、第一版量级小；不设自动故障转移，保留手动恢复通道即可。第二版再评估是否需要 APM / 自动化告警。
- **影响**：部署方案不做双活/高可用；选型优先简单运维（如 Render / Railway / 单实例），不做 Kubernetes。
- **来源**：需求对话 2026-08-12（D-2/D-3 确认）。

## 决策 #12：用户手机号由第三方 Auth 管理 + 4 项数据模型决策

- **日期**：2026-08-12
- **决定**：
  1. **用户手机号**：由第三方 Auth 服务（阿里云短信 + Supabase Auth）管理，本项目服务端不自行存储明文手机号。`encrypted_phone` 字段预留但第一版不使用。
  2. **预设标签清单**：26 个预设标签（兴趣 12：骑行/摄影/动漫/旅游/投资/创业/羽毛球/跑步/读书/音乐/美食/游戏 + 职业 8：AI/程序员/设计师/产品经理/律师/金融/医生/教师 + 生活 6：留学生/数字游民/宠物/咖啡/健身/自驾），用户可自定义新增。
  3. **化名自动生成**：中文 → 姓氏 + 同学/朋友（性别中立）；非中文 → First Name；完全无法解析 → "新朋友"。
  4. **contacts.name 存原文**：owner 自己可见真名，对外仅返回化名，应用层过滤（name 原文绝不返回给非 owner）。
- **影响**：数据模型 schema 定稿；化名规则统一为性别中立风格。
- **来源**：数据模型与隐私设计 D-1/D-2/D-3/D-4 定稿。

## 决策 #13：API 端点设计 4 项决策

- **日期**：2026-08-12
- **决定**：
  1. CSRF：不设独立 token，移动端 Bearer 免疫，Web SameSite=Strict。
  2. 手机号不可解绑（主账号），微信/Apple 可解绑但至少保留一种登录方式。
  3. 批量导入单次上限 500 条。
  4. `/me/graph` 仅返回已展开过的 2 度节点，完整 2 度走增量加载。
- **影响**：27 个 REST 端点规格定稿（认证 7 + 通讯录 6 + 2 度 2 + 关系图 1 + 隐私 3 + 账号 4 + 标签 1 + 杂项 3）；为后端实现提供完整接口契约。
- **来源**：API 端点设计 D-1/D-2/D-3/D-4 定稿。

## 决策 #14：UI 信息架构 5 项决策

- **日期**：2026-08-12
- **决定**：
  1. Web 端仅看图（全屏图 + 隐私设置入口），不做联系人编辑/删除/导入。
  2. 登录国家码仅 +86。
  3. 第一版不展开 3 度，提示"即将推出"。
  4. 统计卡片按分组 + 前 3 高频标签展示。
  5. **图默认仅展示 1 度，但提供"一键展开全部 2 度"按钮**——用户可一键展开所有已注册 1 度联系人的 2 度；也可逐节点单点展开。
- **影响**：14 个页面清单 + 3 Tab 结构定稿；一键展开显著降低"看 2 度"的交互门槛，符合用户想要的"朋友的朋友"浏览体验。
- **来源**：UI 信息架构 D-1~D-5 定稿。

## 决策 #15：技术栈细化 T1-T7 + 采购清单

- **日期**：2026-08-12
- **决定**：
  1. T1 状态管理 = Riverpod
  2. T2 SMS = 阿里云短信服务
  3. T3 数据库 = Supabase Cloud 免费层（ap-southeast-1 新加坡）

  9. 依赖清单、包版本、采购优先级与时间线详见 [技术栈细化与采购清单.md](../design/技术栈细化与采购清单.md)

- **来源**：技术栈细化对话 2026-08-12。
- **⚠️ 待确认**：微信开放平台移动应用需企业资质——个人开发者无法创建微信登录（见技术栈文档 §5.1）。
- **更新（2026-08-12）**：选 C 方案——第一版仅手机号 + Apple 登录，微信登录留接口后补。发布策略：TestFlight + APK 分发，暂不上正式应用商店。

## 决策 #16：开发计划 4 里程碑 + M4 后内测

- **日期**：2026-08-12
- **决定**：
  - 4 阶段：M1 基础设施+数据层（1 周）→ M2 核心 API+Web 看图（2-3 周）→ M3 移动端（3-4 周）→ M4 打磨+分发（1-2 周），总预估 7-10 周。
  - M4 终点 = TestFlight + APK 内测（10-20 人），不是正式上线。
  - D-1：M1 只做手机号 mock，不等阿里云 SMS 审核 + Apple 登录放 M3。
  - D-2：M2 不做 Apple OAuth（需 Xcode + App ID），只做手机号 JWT。
  - D-3：测试数据用 CSV 模板（3 个账号制造 2 度匹配），放 `server/tests/fixtures/`。
  - D-4：M4 后进入内测验证 → 修 bug → 第二版需求评审。内测期间不加新功能。
- **影响**：开发顺序、测试策略、采购时机全部冻结。M1 不再等外部服务开通。
- **来源**：里程碑拆分 2026-08-12（D-1~D-4，全部确认）。
