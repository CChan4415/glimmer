```
│ avatar    │  │    │ allow_contacts  │       │ last_    │  │

              │    └────────────────┘       └──────────┘  │
              │                                            │
              └────────────────────────────────────────────┘
                      (contacts.owner_id → users.id)

┌──────────────┐
│ contact_tags │
├──────────────┤
│ contact_id   │──→ contacts.id
│ tag (string) │
└──────────────┘
```

> 关系说明：
> - `users` : `auth_methods` = 1 : N（一个用户可绑定多种登录方式）
> - `users` : `privacy_settings` = 1 : 1（每个用户一份隐私配置）
> - `users` : `contacts` = 1 : N（一个用户拥有 N 个联系人）
> - `contacts` : `contact_tags` = 1 : N（一个联系人可有多个标签）
> - **匹配**：`contacts.phone_hash` ↔ `users.phone_hash`（没有外键约束，跨表哈希等值匹配）

## 2. 表结构

### 2.1 users — 用户账号表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | UUID | PK, 自生成 | 用户唯一标识 |
| `phone_hash` | VARCHAR(128) | UNIQUE, NOT NULL, INDEX | 手机号加盐哈希，用于匹配"朋友的朋友"。**服务端不存明文手机号**——明文仅存本地 |
| `encrypted_phone` | TEXT | NULLABLE | **应用层加密的手机号明文**，仅用于 SMS 验证码发送。AES-256-GCM 加密，密钥与数据分存（见 §3） |
| `nickname` | VARCHAR(64) | NULLABLE | 用户自设昵称，用作公开化名。若未设 → 系统自动生成（姓氏+称呼，见 §6） |
| `avatar_url` | TEXT | NULLABLE | 头像（可选，第一版可后置） |
| `display_level` | ENUM('pseudonym_only', 'pseudonym_with_group') | DEFAULT 'pseudonym_only' | 自己在别人网络中的展示级别（见 §5） |
| `allow_appear_in_network` | BOOLEAN | DEFAULT TRUE | "我是否出现在朋友的网络中"（全局开关） |
| `allow_contacts_visible` | BOOLEAN | DEFAULT TRUE | "我的联系人是否可被朋友的朋友看到"（全局开关，对他人） |
| `created_at` | TIMESTAMPTZ | NOT NULL | |
| `updated_at` | TIMESTAMPTZ | NOT NULL | |
| `deleted_at` | TIMESTAMPTZ | NULLABLE | 软删除标记（30 天冷静期） |

**索引**：
- `users_phone_hash_idx` (phone_hash) — 2 度匹配的高频等值查询
- `users_deleted_at_idx` (deleted_at) — 清理到期账号

### 2.2 auth_methods — 登录方式表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | UUID | PK | |
| `user_id` | UUID | FK → users.id, NOT NULL | |
| `method` | ENUM('phone', 'wechat', 'apple') | NOT NULL | 登录方式 |
| `identifier` | VARCHAR(256) | NOT NULL | 手机号(本地加密) / 微信 openid / Apple user id |
| `wechat_union_id` | VARCHAR(256) | NULLABLE | 微信 UnionID（跨应用同一微信用户标识，预留） |
| `created_at` | TIMESTAMPTZ | NOT NULL | |

**唯一约束**：`(method, identifier)` — 同一方式的同一标识只能绑定一个账号。

**索引**：`auth_methods_user_id_idx` (user_id)

### 2.3 contacts — 联系人表（核心）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | UUID | PK | |
| `owner_id` | UUID | FK → users.id, NOT NULL, INDEX | 谁的联系人 |
| `name` | VARCHAR(128) | NOT NULL | 联系人真实姓名（**仅 owner 可见**） |
| `phone_hash` | VARCHAR(128) | NULLABLE, INDEX | 手机号加盐哈希（与 users.phone_hash 同算法/同 salt，用于匹配） |
| `group` | ENUM('family', 'colleague', 'friend', 'ungrouped') | DEFAULT 'ungrouped' | 通讯录分组（家人/同事/朋友/未分组） |
| `is_manual` | BOOLEAN | DEFAULT FALSE | 是否为手动联系人（通讯录已删除但仍保留 = TRUE） |
| `last_contacted_at` | TIMESTAMPTZ | NULLABLE | 最近联系时间（用户手动维护） |
| `created_at` | TIMESTAMPTZ | NOT NULL | |
| `updated_at` | TIMESTAMPTZ | NOT NULL | |

**索引**：
- `contacts_owner_idx` (owner_id) — 列出我的联系人
- `contacts_phone_hash_idx` (phone_hash) — 2 度匹配的高频等值查询
- `contacts_owner_phone_idx` (owner_id, phone_hash) — 去重导入

**设计要点**：
- `phone_hash` 可为 NULL——支持"有姓名、无手机号"的纯手动联系人（D-1）
- `name` 是明文真实姓名，但仅 owner 有读权限（RLS 或应用层过滤），任何其他用户不可见
- 通讯录分组来自 iOS/Android 系统分组，不可用时默认 "ungrouped"

### 2.4 contact_tags — 联系人标签表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | UUID | PK | |
| `contact_id` | UUID | FK → contacts.id, ON DELETE CASCADE, NOT NULL | |
| `tag` | VARCHAR(64) | NOT NULL | 标签值（预设或自定义） |

**唯一约束**：`(contact_id, tag)` — 同一联系人不重复打同标签

**索引**：`contact_tags_contact_idx` (contact_id)

### 2.5 tag_presets — 预设标签库（应用层维护）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `tag` | VARCHAR(64) | PK | 预定义标签值 |
| `category` | VARCHAR(32) | NULLABLE | 标签分类（兴趣/职业/其他），仅用于前端分组展示 |
| `sort_order` | INT | DEFAULT 0 | 前端展示排序 |

> 第一版预设标签清单在 §6 D-2 中定。此表仅为前端标签选择器提供数据源，可由管理端修改后实时生效。

## 3. 安全存储方案：手机号

### 3.1 两类手机号的区别

| 类别 | 存储位置 | 存储方式 | 用途 |
| --- | --- | --- | --- |
| 用户自己的手机号（账号） | 服务端 `users.encrypted_phone` | AES-256-GCM 应用层加密 | SMS 验证码发送 |
| 联系人的手机号（第三方） | **服务端仅存哈希** `contacts.phone_hash` | 加盐哈希（不可逆） | "朋友的朋友"匹配；明文仅 App 本地存储 |

### 3.2 加密方案（用户手机号）

- 算法：AES-256-GCM（认证加密，防篡改）。
- 密钥管理：加密密钥存于环境变量（非代码仓库），与数据库分离；密钥轮换预留字段在 `users` 表（`key_version` 可选）。
- 解密：仅在发送 SMS 验证码时解密，解密后的明文不缓存、不写日志。
- **第一版简化**：若用 Supabase Auth / 阿里云短信服务，手机号由第三方 Auth 服务管理，`encrypted_phone` 可为空——本项目不自行存明文手机号（[见 D-1 决定](#9-决策记录本文档)）。

### 3.3 哈希方案（联系人手机号）

- 算法：HMAC-SHA256(phone_number, global_salt)，global_salt 存于环境变量。
- 同一手机号 → 同一哈希（可匹配）；不同 salt → 不同哈希（salt 轮换后需全量重哈希）。
- 服务端任何时候不存、不打印、不写日志中的明文联系人手机号。

## 4. 核心查询："朋友的朋友"（2 度发现）

> 以下为数据库层逻辑。封装在 `repos/` 查询层（决策 #08），业务层通过接口访问——未来替换存储引擎时仅改此层。

### 4.1 查询 Step 1：我的 1 度已注册联系人

```sql
-- 输入：我的 user_id = $me
-- 找出我导入的联系人中，哪些人已注册（phone_hash 匹配）

SELECT c.id AS contact_id,
       c.name AS real_name,          -- 仅返回给我自己
       c.phone_hash,
       c."group",
       u.id AS matched_user_id,
       u.nickname,
       u.display_level
FROM contacts c
JOIN users u ON c.phone_hash = u.phone_hash
WHERE c.owner_id = $me
  AND u.allow_appear_in_network = TRUE
  AND u.deleted_at IS NULL;
```

> 返回结果中 `real_name` 仅在前端展示给我的时候使用；传给其他用户的 API 响应中不包含此字段。

### 4.2 查询 Step 2：为某个 1 度已注册联系人，查其 2 度

```sql
-- 输入：中间人 user_id = $friend_id, 我的 user_id = $me
-- 返回该中间人的联系人（= 我的 2 度），受双向隐私开关约束

SELECT c2.id,
       c2.name,              -- 应用层不返回，仅用作化名生成
       c2.phone_hash,
       c2."group",
       COALESCE(u2.nickname, gp.pseudonym(c2.name)) AS display_pseudonym,
       u2.display_level,
       u2.id AS target_user_id
FROM contacts c2
LEFT JOIN users u2 ON c2.phone_hash = u2.phone_hash
WHERE c2.owner_id = $friend_id
  AND ($friend_privacy.allow_contacts_visible = TRUE)    -- 中间人开关
  AND ($my_privacy.allow_appear_in_network = TRUE)       -- 我自己的开关（确保我的请求合法）
  AND (u2.id IS NULL OR u2.allow_appear_in_network = TRUE) -- 目标本人的开关
  AND (u2.id IS NULL OR u2.deleted_at IS NULL);
```

> 三层隐私检查在查询中同时生效；若中间人关闭 `allow_contacts_visible`，整个 2 度视图为空。

### 4.3 查询模式总结

| 场景 | 触发 | 隐私约束 |
| --- | --- | --- |
| 我浏览自己的 1 度联系人 | 打开我的关系图 | 无（自己的数据） |
| 我展开某 1 度朋友（已注册）的 2 度 | 点击节点 | 三步检查：我→中间人→目标，各由双方开关决定 |
| 1 度朋友未注册（无匹配用户） | 不展开，无法点 | 显示"尚未注册"标识 |
| 我关闭"我的联系人可被看到" | 别人看我的联系人列表 → 空 | 整个 2 度视图不返回 |

## 5. 隐私模型在数据层的表达

### 5.1 双向开关与展示级别

```
                  ┌──────────────────────────────┐
                  │       users (我自己)          │
                  │  allow_appear_in_network      │ ← 我是否出现在任何人的朋友网络中
                  │  display_level               │ ← 出现时显示什么
                  │  allow_contacts_visible       │ ← 我的联系人是否暴露给别人
                  │  nickname                     │ ← 我的化名（公开形象）
                  └──────────────────────────────┘

  别人看我 (2度)                      别人看我的联系人 (2度)
       ↓                                     ↓
  allow_appear_in_network              allow_contacts_visible
  = TRUE 时才出现                      = TRUE 时才暴露
       ↓
  display_level 决定粒度:
  pseudonym_only → "陈先生"
  pseudonym_with_group → "陈先生 · 同事"
```

### 5.2 展示规则速查表

| 我是 | 我设置 | 中间人设置 | 搜索者看到我 |
| --- | --- | --- | --- |
| 已注册 | allow_appear=TRUE, pseudonym_only | allow_contacts=TRUE | "陈先生" |
| 已注册 | allow_appear=TRUE, pseudonym_with_group | allow_contacts=TRUE | "陈先生 · 朋友" |
| 已注册 | allow_appear=FALSE | 任何 | **不出现** |
| 未注册 | N/A | allow_contacts=TRUE | "陈先生"（系统从 name 自动生成化名） |
| 未注册 | N/A | allow_contacts=FALSE | **不出现** |
| 已注册 | allow_appear=TRUE | allow_contacts=FALSE | **不出现** |

### 5.3 认领机制（第二版，预留设计）

> 第一版不做认领流程，但 schema 预留：

- 未注册用户的 phone_hash 存在 `contacts` 表中，无对应 `users` 行。
- 第二版注册后：`users.phone_hash` = `contacts.phone_hash` 自动匹配 → 该用户可在"通知"中看到自己被谁录入 → 触发认领（归并联系人记录、设置自己的隐私偏好）。
- 第一版注册后的即时匹配走 4.1 的同一逻辑（JOIN 等值哈希），不需要额外数据结构。

## 6. 化名规则

### 6.1 已注册用户

- `nickname` 已设 → 直接使用 nickname。
- `nickname` 未设 → 系统从 `name` 自动生成（服务端执行，仅用于公开化名生成，name 原文不返回）。
  - 中文名（2-4 字）：姓氏 + "先生/女士"（如"陈先生"）——性别不定时用"用户"兜底（"陈用户"不妥 → 统一用姓氏 + "朋友"）。
  - 非中文名（拉丁字母等）：名（first name）+ "Friend"（如"John Friend"），或首字母化。"John S." + "Friend"。
  - 无法解析：留默认"用户"。

> 化名规则选型见 D-4。

**【需决策，见 D-4】**

### 6.2 未注册用户

- 系统从联系人 `name` 自动生成化名（规则同 6.1），不暴露 `name` 原文给他人。
- 第二版认领后，用户可改为自己的 nickname。

### 6.3 手机号无姓名（D-1 的兜底）

- 有手机号但无姓名 → 自动填充 "未知联系人"（owner 可后续编辑），对外化名同此。

## 7. 数据迁移与扩展预留

### 7.1 图数据库迁移点

| 当前 | 迁移后 | 触发条件 |
| --- | --- | --- |
| 递归 CTE 做 2 度遍历（Postgres） | Neo4j / Memgraph (Cypher) | 联系人超 10 万、需要 3 度路径分析 |
| 查询封装在 `repos/graph.py` | 替换该层实现 | 决策 #08 模块化约束 |
| 当前 2 度仅 JOIN 即可 | 3 度需要 CTE，超过 3 度需图数据库 | 更复杂的路径查询需求 |

### 7.2 标签体系扩展

- AI 自动打标签（P1）接入时：新增 `ai_suggested_tags` 结果表，不直接写 `contact_tags`——用户确认后才写入，防止 AI 错误污染数据。

### 7.3 用户表未来字段

| 字段 | 版本 | 说明 |
| --- | --- | --- |
| `claimed_contacts` | 第二版 | 认领后的联系人归并记录 |
| `invite_code` | 第二版 | 邀请码（冷启动传播） |
