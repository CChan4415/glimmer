# 技术选型：Glimmer / 流萤

> 状态：已定稿（2026-08-11）
> 决策依据：单人开发、熟悉 Python、目标双端同时（iOS + Android）

## 1. 决策约束

| 约束 | 内容 | 对选型的影响 |
| --- | --- | --- |
| 开发背景 | 熟悉 Python | 后端锁定 Python 生态 |
| 团队规模 | 单人开发 | 优先托管服务、减少运维；MVP 求快 |
| 平台 | iOS + Android 双端同时 | 必须跨平台框架，不做原生双端 |
| 阶段 | Idea 验证期（MVP 4 功能） | 技术栈可换层从简，核心层做对 |

## 2. 技术栈总览

| 层 | 选型 | 平替 | 选择理由 |
| --- | --- | --- | --- |
| 客户端 | **Flutter** | Flet（纯 Python）、React Native、原生双端 | 一套代码双端；图可视化生态成熟（graphview）；Dart 语法贴近 Python，学习成本低 |
| 后端 | **FastAPI** | Django、Flask | Python 生态、类型提示、自动生成 API 文档（/docs），异步性能好 |
| 数据库 | **PostgreSQL** | SQLite（MVP 起步）、MySQL | 递归 CTE 做多度图遍历；Row-Level Security 与四层可见性模型天然契合 |
| Auth | **Supabase Auth** | Authlib 自建 OAuth、Auth0 | 单人开发免去 OAuth 轮子；Apple/Google/邮箱登录开箱即用 |
| 图查询 | **递归 CTE**（Postgres） | Neo4j / Memgraph（规模上来后） | MVP 5,000 节点量级毫秒级；封装查询层，后期可平滑迁移图数据库 |
| AI | **Claude API**（anthropic Python SDK） | GPT / Gemini / 本地开源 | 服务端调用；API 封装成独立模块，可替换 |
| 推送（P1） | **FCM + APNs**（经第三方如 OneSignal） | 站内通知先顶替 | MVP 引荐通知可用站内轮询，推送后置 |
| 部署 | **Docker + Render/Fly.io** | Railway、AWS Lightsail | 单人最省心；数据库用 Supabase 托管或云 PG |
| 版本管理 | Git + GitHub | — | monorepo：`app/`（Flutter）+ `server/`（FastAPI） |

## 3. 关键决策详解

### 3.1 客户端为什么是 Flutter 而不是纯 Python 方案

这是"熟悉 Python"约束下最重要的取舍。纯 Python 移动端选项：

- **Flet**：用 Python 写 Flutter UI，最贴近舒适区，但生态小、复杂交互受限、**图可视化无成熟库**（而关系图谱是产品的 P1 功能）
- **Kivy**：UI 观感差、打包繁琐，双端发布体验不佳，不建议

结论：客户端选 Flutter（Dart 只需学 UI 层语法，业务逻辑全部在 FastAPI），把 Python 用在刀刃上。

### 3.2 隐私模型与数据库的契合（核心层，必须一次做对）

四层可见性模型直接落库为每条关系记录的 `visibility` 字段：

- L1 私人 → `visibility=1`（仅本人可查）
- L2 匿名共享 → `visibility=2`（查询时脱敏为"某律师"）
- L3 半公开 → `visibility=3`（属性可见，无姓名）
- L4 授权公开 → `visibility=4`（双方同意后解锁姓名，需关联授权表）

Postgres RLS 可让数据库层强制过滤，应用层再补脱敏展示。**数据模型设计详见后续《数据模型与隐私设计》文档**（这是全项目最先要产出的设计）。

### 3.3 图遍历：递归 CTE 先跑，Neo4j 后置

```sql
-- 示意：2 度内、带可见性过滤的遍历
WITH RECURSIVE reach AS (
  SELECT id, 1 AS depth FROM edges WHERE from_id = $me
  UNION ALL
  SELECT e.to_id, r.depth + 1 FROM edges e
  JOIN reach r ON e.from_id = r.id
  WHERE r.depth < 3 AND e.visibility >= $threshold
)
SELECT * FROM reach;
```

- MVP 数据量（≈5,000 节点）下毫秒级，无需图数据库
- 业务查询封装成独立查询层（repository），数据量到达 10 万级或需复杂路径分析时，仅替换该层为 Neo4j（Cypher），其余不动

### 3.4 Auth 方案

- MVP 直接使用 **Supabase Auth**：免维护 OAuth 流程，Apple/Google/邮箱齐备，免费层够用
- 若后期要完全自控，用 **Authlib** 在 FastAPI 内自建 OAuth，可迁移

## 5. 平替技术栈速查

| 想换什么 | 换成 | 触发条件 |
| --- | --- | --- |
| 数据库 | SQLite | MVP 本机调试阶段，零依赖起步 |
| 图存储 | Neo4j / Memgraph | 节点 10 万级、3 度遍历变慢、需要路径分析 |
| 后端框架 | Django（含 Admin） | 需要后台管理界面，接受重框架 |
| 客户端 | Flet | 明确放弃图可视化，坚持纯 Python |
| Auth | Authlib 自建 | 需要完全掌控登录流程 |
| 部署 | Railway / Fly.io | Render 不满足时平替，用法接近 |
